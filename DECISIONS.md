# Decisions

Defaults picked while building, so they can be revisited in one place.
Format: what, why, and how to change it.

## Phase 1: Foundation

1. **No locale segment in URLs.** Locale = `?lang=fr|ar` (sets a cookie) → `NEXT_LOCALE` cookie → `Accept-Language` → French. The spec's routes (`/tarifs`, `/app/menu`) carry no locale, and a root `[locale]` segment can't coexist with the root `[slug]` public menus. Static routes win over `[slug]`, and every top-level route name is in `reserved_slugs`. Public menus fall back to the restaurant's `default_locale` (phase 3).
2. **Tailwind v4 + shadcn/ui conventions.** `components.json` is configured (new-york, lucide, `@/components/ui`, `cn` in `lib/utils/cn.ts`) so `pnpm dlx shadcn add <x>` works. The base components are hand-written on Radix primitives to use our tokens and logical properties rather than shadcn's default theme.
3. **Library versions:** Next 15.5, React 19.1, next-intl 4, Zod 4, `@tanstack/react-table` pinned to v8 (v9 changed its API), vaul for bottom sheets, sonner for toasts, react-easy-crop for the cropper.
4. **Billing columns hidden with column grants.** `authenticated` cannot select `plan`, `paid_until`, `payment_reference`, `referral_code`, `referred_by` on `restaurants`. Owners and super admins read them from the `restaurant_billing` view. `status` and `trial_ends_at` stay readable by staff because the app needs them to show the locked state.
5. **Restaurant creation, slug changes, status changes go through RPCs** (no direct insert on `restaurants`). `change_slug()` keeps the old slug in `slug_history` forever.
6. **Subscription lock is enforced in RLS**, not only in the UI: `can_edit_menu()` / `can_edit_settings()` return false when status is `expired` or `suspended`. Handling waiter calls stays allowed when expired.
7. **Staff vs owner split:** staff write menu tables (categories, items, variants, extras, schedules). Tables, hours, exceptions, social links, delivery zones and restaurant settings are owner-only writes; staff can read them.
8. **`restaurant_id` is denormalized onto `item_variants` / `item_extras`** (kept in sync by trigger) so RLS checks are a single function call.
9. **`menu_events` is indexed, not partitioned:** btree on `(restaurant_id, created_at desc)` + BRIN on `created_at`. Partition by month if it passes ~50M rows.
10. **Payment references** come from a sequence: `QR-0001`, `QR-0002`, … Referral codes are 6 chars without ambiguous letters.
11. **Weekdays are 0 = Sunday … 6 = Saturday** (JS `Date.getDay()`), times in the restaurant's timezone.
12. **Wilaya codes 1–58** (2019 division; list in `lib/dz/wilayas.ts`). Phase 2 tightened the original 1–69 check.
13. **Arabic prices render `1200 دج` as an isolated LTR run** (`<bdi dir="ltr">`), digits always Western; French uses U+202F as thousands separator.
14. **Local DB tests without Docker:** `pnpm db:test` boots a throwaway Postgres, loads `supabase/tests/local/supabase_shim.sql` (roles, `auth.uid()`, storage schema, a tiny pgTAP subset), then migrations, seed and `supabase/tests/*.sql`. The same `rls.sql` runs unchanged under `supabase test db`.
15. **DB types** are generated by `pnpm db:types` (our introspection script, same shape as `supabase gen types`). Swap to `supabase gen types typescript --local > lib/supabase/types.ts` whenever the Supabase CLI and Docker are available.
16. **`/dev/ui` is hidden in production** unless `ENABLE_DEV_UI=true`.
17. **Plan prices** in `platform_settings`: 2 500 DA/month, 13 500 DA/6 months, 24 000 DA/year, kit 6 000 DA (confirmed). Editable in admin settings (phase 8).

## Phase 2: Auth + onboarding

18. **Name and domain: Liinky, `liinky.app`** (`APP_NAME`, `NEXT_PUBLIC_APP_DOMAIN`).
19. **No SMS anywhere.** Accounts are phone + password, password typed twice at signup, no code at signup.
20. **Phone identity without SMS:** Supabase Auth's phone login requires an SMS provider, so each phone maps to a fixed internal email `p213XXXXXXXXX@phone.invalid` (`.invalid` is reserved and can never receive mail). `profiles.phone` (unique) is the real identity. Accounts are created server-side with the service key, so **public signup must be disabled** in Supabase Auth settings (`GOTRUE_DISABLE_SIGNUP=true`). Email confirmation is irrelevant (created as confirmed).
21. **Admin-issued codes** (`phone_codes`) replace OTP for (a) "Vérifier mon numéro" in account settings and (b) "Mot de passe oublié". The user asks; the request shows up on `/admin/codes`; the admin calls, generates a 6-digit code and reads it out. Codes live **2 minutes** (`code_ttl_seconds`), allow **5 attempts**, are stored as SHA-256 hashes (salted with the request id) and shown to the admin once. Admins can also generate a code with no prior request (during a call). Both waiting screens poll every 3 s and show the countdown. A successful password reset also marks the phone verified (the admin called that number).
22. **"Mot de passe oublié" says when a number has no account.** It helps owners who mistype; the risk (learning that a phone belongs to a restaurant owner) is low and the endpoint is rate-limited.
23. **Phone verification is optional** and doesn't gate anything yet; the home screen nudges until it is done.
24. **One owned restaurant per account** (`create_restaurant` refuses a second). Staff can belong to others via invites.
25. **Uploads go through server actions** (validated + resized with sharp, stored with the service key), never directly from the browser. Storage RLS policies stay as defense in depth.
26. **Onboarding step 4 (AI review) is skipped** until phase 6: step 3 goes straight to 5. Photo/PDF import buttons show "Bientôt".
27. **Restaurant default language = the language the owner used during setup.** Generated table labels ("Table 3" / "طاولة 3") follow it.
28. **Slugs:** generated from the name and kept in sync until edited; Arabic-only names fall back to `restaurant-<commune>`. Availability is checked live with a free alternative suggested.
29. **No first-order check for diners** (confirmed). `first_order_otp` stays false; abuse is handled by fake-order flagging and platform-wide blocked phones (phase 5).
30. **Temporary public menu page** at `/[slug]` proves links work (slug history 301s, table vs order mode, paused state). Phase 3 replaces the rendering with the 9 templates.
31. **Docker-free dev stack** (`pnpm stack:start`): Postgres + GoTrue + PostgREST binaries + a small Node gateway that also serves Storage from disk (no storage RLS there). Prefer `supabase start` when Docker exists.

## Phase 3: Public menus

32. **Two root layouts.** `app/(site)` (marketing, auth, owner app, admin) and `app/(menu)` (public menus). Menus get a cookie-free `<html>` with no i18n runtime, toaster or app fonts, so they can be statically cached and stay light.
33. **Menu URLs are rewritten, not routed.** The middleware turns `/{slug}` and `/{slug}-menu` into `/r/{lang}/{segment}`, an ISR route (`revalidate = 3600` + on-demand `revalidateTag("menu:{slug}")` from every owner edit). Language order: `?lang=` > diner's cookie > browser `Accept-Language` > restaurant default (`default` variant). Every first path segment owned by the app is listed in `lib/routes.ts` and must be a reserved slug (unit-tested). Note: Next marks rewritten responses `Cache-Control: private`; the server-side ISR cache still serves them (~20 ms). Only matters behind a CDN.
34. **Old slugs 301 in the middleware**, which can keep `?t=` (printed table QR codes) and `?src=`. It asks `resolve_public_slug` and caches the answer per instance for 60 s. The page keeps a query-less fallback redirect.
35. **Device-side state.** The cached HTML is shared, so time- and visitor-dependent things are computed in the browser: open/closed (restaurant time zone), menu schedules, the table label from `?t=`, favorites (localStorage per restaurant), analytics beacon.
36. **Templates = one shared `MenuApp`** (search, scrollspy tabs, item and info sheets, favorites, analytics) + per-template `Header`, `CategoryTabs`, `ItemCard`, `ItemSheet` (+ optional `SectionHeader`, `DishOfDay`) and a `--m-*` theme. The template is picked in a client component with `next/dynamic`: a server-side import of all nine put every template into the page's chunks.
37. **Sheets use native `<dialog>`** (focus trap, Esc, inert background) instead of a dialog library, to keep diners' JS small.
38. **Fonts on menus are self-hosted** (`public/fonts/menu`, fetched by `scripts/fetch-menu-fonts.mjs`, all OFL). Each page preloads only its template's display face (+ Cairo Arabic on Arabic pages); Latin body text uses the system UI font. `next/font` remains for the site/app, with `preload: false` because Next attached those preloads to menu routes through the shared stylesheet. Result: LCP 1.7–2.3 s, Lighthouse mobile performance 97–99.
39. **JS budget.** Table mode loads ~148 KB gzipped: ~125 KB is the React 19 + Next 15 App Router runtime (present on every App Router page), ~15 KB shared menu code (incl. `next/image`), ~8 KB for the chosen template. The spec's < 100 KB isn't reachable with the App Router runtime alone; the Lighthouse target (≥ 90) is met with margin. Going lower would mean serving table mode outside React (static HTML + a small script).
40. **Public menu code avoids `tailwind-merge`** (`cx()` instead of `cn()`), saving ~8 KB.
41. **Table links are `noindex`** (duplicates of the order link) and canonical to `/{slug}`. Lighthouse SEO on table links is 90 because of that, by design.
42. **Preview route** `/apercu/{template}/{fr|ar}/{slug}`: any restaurant in any template and language, uncached, no analytics, `noindex`. Used for template QA now and the appearance editor's live preview in phase 4.
43. **Order mode in phase 3 = browse only** (sizes and extras shown in the item sheet). Cart, checkout and WhatsApp land in phase 5; the waiter-call button with them.
44. **Photos:** seed items have none, so cards show a themed initial placeholder. Photo-heavy layouts (Grill rows, Traditionnel dish of the day) shrink when there's no photo.

## Phase 4: Owner menu management

45. **Multi-row writes go through `SECURITY INVOKER` RPCs** (`save_item`, `reorder_*`, `set_prices`, `bump_prices`, `save_translations`): one transaction, while RLS and the subscription lock still decide. `save_item` replaces sizes and extras wholesale.
46. **Staff manage the menu** (categories, items, prices, translations, schedules, sold-out) and can see the share hub. Appearance and tables are owner-only, like other settings.
47. **Deletes are soft with an Undo toast** (categories, items). Tables are hard-deleted after a confirm sheet (calls and events keep `table_id = null`).
48. **Sold-out toggles are optimistic** with Undo; a failure (e.g. expired subscription) rolls the switch back and shows why.
49. **Bulk price change is an amount in DA** (+50 / -20) on the whole menu or one category; sizes follow; never below 0. No percentage: Algerian menus move in round DA steps.
50. **Brand color is a fixed palette** of 8 colors that all keep white text at 4.5:1 (plus "template color"). Picking one also sets the template's on-accent text to white.
51. **Live preview** is an iframe of `/apercu/...` with `?accent=` for the unsaved color; it reloads on template/color/language/logo/cover changes.
52. **Dish photos**: up to 4, cropped 4:3 in the browser, resized to WebP (max 1600 px) on the server, first one is the main photo. Removed photos are deleted from Storage on save; uploads abandoned before saving are left for a purge job (TODO).
53. **QR images are drawn in the browser** (canvas + `qrcode`, page fonts, so Arabic shapes correctly): QR PNG/SVG, Instagram story 1080×1920, post 1080×1080, per-table cards, ZIP via `jszip` (loaded on demand).
54. **The table PDF uses `@react-pdf/renderer` on the server** with static Cairo TTFs in `lib/pdf/fonts` (fontkit can't embed variable WOFF2). 6 cards per A4 page with the Kabyle band, QR, table name and the scan line in each enabled language.
55. **Tracked links**: the share hub lists `?src=ig|fb|tt|wa|poster` variants of the order link; visits per source over 7 days come from `channel_stats()`.
56. **Rate limits per IP are loose** (signup 30/h, login 100/15 min, reset 20/h) and skipped for loopback/unknown IPs: Algerian mobile carriers put many users behind one IP (CGNAT). Per-phone limits do the real work.
57. **Dev stack tracks applied migrations** (`pnpm stack:migrate`).

## Phase 5: Ordering and waiter calls

58. **Orders are validated and priced by the database** (`submit_order`, security definer, callable by anon). The browser sends item/size/extra ids and quantities only; prices, availability, minimum, zone fee and the restaurant's WhatsApp number come back from Postgres. Errors are codes (`below_minimum`, `zone_required`, `phone_blocked`, …) mapped to FR/AR messages; an unavailable item is dropped from the cart.
59. **WhatsApp is the order channel.** After `submit_order` the diner's browser opens `wa.me/{restaurant}?text=…` with the order written in the diner's language (`lib/whatsapp/message.ts`); the order row exists before the message is sent, so stats count orders "sent to WhatsApp", not confirmed ones. Cash on delivery/pickup only.
60. **No ordering while closed.** When opening hours say closed, the item sheet and cart show "Fermé pour le moment · commandes à partir de 11:00" instead of the buttons. Menus without hours are always open.
61. **Cart lives in localStorage per restaurant** (`liinky:cart:{id}`); the diner's name/phone/address are remembered on the device (`liinky:customer`) to speed up the next order. No customer accounts.
62. **Abuse control:** rate limits per phone (5 orders / 10 min) and per browser session; owners flag fake orders from the stats log (`flag_order`), each flag is a report on the phone, and after `platform_settings.block_after_reports` reports (2 by default) the number is blocked on every restaurant. Unflagging removes the report.
63. **Waiter calls**: one button on table links (waiter / bill / water), one open call per table and kind within `platform_settings.waiter_call_cooldown_sec` (the button shows the countdown), plus a rate limit per browser session. Calls land in `/app/appels` and in a header chip on every owner screen; "J'y vais" marks them handled. Only today's calls are shown.
64. **Live updates = Supabase Realtime + polling.** `/app/appels` subscribes to `waiter_calls` changes when Realtime exists and polls as a fallback (every 30 s with Realtime, every 5 s without; paused while the tab is hidden). `NEXT_PUBLIC_REALTIME=off` disables the subscription where no Realtime server runs (the local stack writes it). Sound is opt-in (browsers block autoplay) with a WebAudio beep; vibration where supported.
65. **Order settings are owner-only** (`/app/reglages/commandes`): on/off, WhatsApp number, delivery and/or takeaway (at least one), delivery zones with fees (no zones = free delivery), minimum order, displayed delay.
66. **Stats** (`restaurant_stats`, security invoker): 7/30 days, visits per day split table/order link (stacked bars in a validated two-color pair), peak hours, channels, tables (with calls), most viewed dishes, orders count/amount, plus the order log with flagging. Ranked lists are plain bars rather than charts. Recharts is loaded only on `/app/stats`.
67. **Menu sheets take a fixed `name` for their ARIA ids** instead of `useId`: `next/dynamic` (used to load the template) renders a server-only sibling, so generated ids differed between server and client and broke hydration.

## Phase 6: AI menu import

68. **`MenuExtractor` and `MenuTranslator` interfaces** (`lib/ai`). Default implementation: Claude through the Anthropic SDK, model from `AI_MODEL` (default `claude-opus-5-5`), structured output validated with Zod (`betaZodOutputFormat` + a second `safeParse`). Effort `high` for reading menus, `low` for translations. Server-side refusal fallback is on (`fallbacks: "default"`). `AI_PROVIDER=fixture` returns canned menus for local dev and E2E (refused in production unless `ALLOW_AI_FIXTURE=true`).
69. **The model copies, our code parses.** Prices come back exactly as printed (`"1.100"`, `"11 00"`, `"١٢٠٠ دج"`) and go through `parsePrice`; a price we can't parse is flagged, never guessed. Names are copied per script (Latin → `fr`, Arabic → `ar`) and never translated during extraction, so confidence stays meaningful; translation is a separate, reviewable step.
70. **Orange = check this.** A field is flagged when the model's confidence is below 0.7, the price can't be parsed, or a dish has no price. Editing a field clears its flag. Sections repeated across photos are folded automatically; duplicate dishes (accent/case/Arabic-letter-insensitive names) are only suggested, and the owner chooses "Fusionner" or "Garder les deux".
71. **Synchronous import.** The server action uploads to the private `imports` bucket, opens the import (`begin_ai_import`: membership, quota, 10/hour), waits for the extractor (usually < 1 min) and stores the draft on `ai_imports.result`. No queue or Edge Function: one request, a progress screen, and the draft survives a reload (step 4 / `/app/menu/importer/{id}` reopen it). Photos are shrunk in the browser (2000 px JPEG) before upload and normalized again with sharp; PDFs up to 20 MB (server action body limit raised to 22 MB).
72. **Quota:** trial restaurants get `platform_settings.ai_imports_per_trial` (5) imports; failed ones don't count. Paid plans are only rate-limited (10/hour). Auto-translate is limited to 20 requests/hour per restaurant.
73. **Applying is additive.** `apply_ai_import` adds dishes (with sizes) to categories matched by name, or creates them; it never deletes or overwrites existing dishes, and an import can be applied once. Onboarding: step 3 (photos/PDF/manual) → step 4 (review) → step 5; manual entry still skips step 4.
74. **Auto-translate fills suggestions, not the menu.** "Traduire automatiquement" (onboarding step 5 and `/app/menu/traductions`) puts translations into the form; nothing is saved until the owner saves.

## Phase 7: Billing, kit, subscription engine, referral

75. **One state machine, two copies.** `lib/subscription/state.ts` (unit-tested, used for banners) and `public.subscription_status_for()` (used by the database) implement the same rules: trial → grace (`grace_days`) → expired; paid → active until `paid_until` → grace → expired; suspended/paused are admin-only. A payment brings any restaurant back to active.
76. **When the state moves:** nightly via pg_cron (`subscription-tick`, 01:15 UTC, scheduled by the migration when the extension exists) or `POST /api/cron/nightly` with `CRON_SECRET` (Coolify scheduled task); and on every owner-app request (`sync_subscription` in `getMyRestaurant`), so a restaurant never stays "active" past its date waiting for the job. Both are idempotent.
77. **Money is computed by the database.** `submit_payment` takes plan, method and receipt path; amount and reference come from `platform_settings` and the restaurant. One pending payment at a time. `approve_payment` adds the plan's months to max(now, paid_until) (Postgres month arithmetic, mirrored in TS) and stores the period on the payment. Admin approvals, rejections and kit stages are audited.
78. **No SMS: in-app notifications** (you chose no SMS provider). Payment approved/rejected, trial ending (2 days before = day 12), renewal due (7 days before), grace, expired, kit mockup/stages and referral rewards become rows in `notifications` (deduplicated by key), shown in a header bell and `/app/notifications`. Billing notices are owner-only.
79. **PDF receipts are generated on demand** (`/app/abonnement/recu/{id}`, approved payments only) rather than stored; always in French, like other Algerian business documents. Receipt photos/PDFs go to the private `receipts` bucket; owners see them through short-lived signed links, signed server-side after the rows were read through RLS.
80. **Kit = cash on delivery for kit + annual plan.** `cod_amount = kit_price + price_annual` (6 000 + 24 000 = 30 000 DA). Owner orders (stands/posters, address, phone), admin uploads a mockup, owner approves or requests changes (any number of rounds), admin moves printed → shipped (tracking) → delivered → paid. "Paid" records an approved COD payment and starts 12 months from the delivery date (or after the running subscription if it ends later). One open kit order at a time.
81. **Referral:** each restaurant has a code; `/inscription?ref=CODE` stores it (httpOnly cookie, 30 days) and `create_restaurant` links the new restaurant. On the referred restaurant's first approved payment (or paid kit), the referrer gets one month: added to its trial if it is still in trial, else to its subscription. One reward per referred restaurant.
82. **Banners live in the owner layout** (all screens): trial, trial ending, renewal due (≤ 7 days), grace (days until lock), expired. Staff see the lock notice without billing links.
83. **Admin screens come in phase 8.** Approve/reject and kit stages exist as audited RPCs now (E2E drives them with an admin session).

## Phase 8: Admin

84. **Two-factor is enforced by the database, not only the app.** `is_super_admin()` requires an `aal2` JWT (password + TOTP via Supabase MFA). A super admin with a password-only session is a regular user to RLS and every admin RPC. The app adds the same check in the middleware and `requireSuperAdmin()` (verified claims via `getClaims()`), redirecting to `/admin/mfa`, which enrolls a TOTP app on first use (QR + secret) and verifies it afterwards.
85. **Every admin mutation is an audited RPC.** Direct writes on `admin_calls`, `admin_notes`, `reserved_slugs`, `platform_settings` and `templates` are revoked; trial extension, manual activation, suspension, notes, calls, settings, template switches, reserved slugs, payment and kit decisions and "view as" all write `audit_log`. The journal filters by action prefix, restaurant and dates, and exports CSV (UTF-8 BOM, formula-safe).
86. **Read-only impersonation** ("Voir son tableau de bord"): an httpOnly cookie makes `getMyRestaurant()` return that restaurant for the super admin; the middleware answers 403 to every non-GET request under `/app` (so no server action can run), the two buttons that call Supabase from the browser are disabled, and a banner offers "Quitter" (a plain POST to `/admin/vue/sortir`). Starting a view is audited; the cookie lasts one hour.
87. **Daily call list** = trials ending within 2 days (and those that entered grace in the last 3 days), most visited first, with one-tap outcome logging. **Renewals** = paid subscriptions ending within 30 days or in grace, with whether the reminder notification went out and whether a receipt is pending.
88. **Payment queue** shows the receipt (signed link, image inline) next to plan, amount, method and reference; reject takes a preset reason (illegible, wrong amount, missing reference, reused, not received) or a free one. **Kit board** is a drag-and-drop kanban: only the next stage is accepted (the owner approves mockups); moving to "Expédié" asks for the tracking number; mockups are uploaded from the card.
89. **Settings** are range-checked twice (Zod in the action, a CHECK constraint in the table); the verification-code settings replaced the old SMS ones (no SMS provider). `first_order_otp` stays off and is not exposed (you chose no first-order check).
90. **Login limiter counts failed attempts only** (10 per phone, 100 per IP per 15 min). Busy owners and admins logging in often are never locked out; guessing still is.
91. **Admin is desktop-first** (1440 px) with a sidebar and centered dialogs; it still works on a phone (horizontal nav, scrollable tables and board).

## Phase 9: PWA, offline, polish

92. **Serwist, built after `next build`.** `@serwist/next`'s webpack plugin does not run under Turbopack, so the worker (`sw/sw.ts`) is compiled by `serwist build` (config `serwist.config.mjs`) into `public/sw.js` (git-ignored). It registers in production only.
93. **Runtime caching only, no app precache.** Precaching every chunk would make each deploy download megabytes to every diner's phone. Instead: menus (any `/{slug}` or `/{slug}-menu` navigation) are network-first with a 5 s timeout and a 30-menu cache; menu photos and `_next/image` are stale-while-revalidate; static chunks, fonts and icons are cache-first; the owner home and menu pages are network-first. Non-GET requests and other origins (except Supabase public storage) never touch the cache.
94. **The offline fallback is a static `public/offline.html`** (French + Arabic, inline CSS, no JS bundle), precached with its icon. A Next page as fallback crashed when its chunks weren't cached yet. Menus opened before show a "menu saved on this phone, may be out of date" bar when offline.
95. **Owner offline queue** covers what the spec asked: sold-out toggles and price edits. Made while offline (or when the request never reaches the server), they are kept in `localStorage` per restaurant, merged (last value per dish wins), shown as "N changes waiting for network", and replayed on reconnect with a toast. Other edits need the network; the existing offline banner says so.
96. **Install prompt** on the owner home: the browser's prompt on Android/desktop, the "Share → Add to Home Screen" hint on iPhone; dismissed once, gone. Manifest start URL is `/app` (it is the owners' app; diners just open links).
97. **Team = staff invited by phone, joined by link.** No SMS: the owner creates the invite and sends the link by WhatsApp (or copies it). Anyone holding the link can accept it once; it is single-use, the same phone gets the same link, at most 20 staff. Staff see menus, calls and stats, never billing, team or settings. Removing a member and cancelling an invite are audited.
98. **Restaurant info is the onboarding form in "settings" mode** (one form to maintain). Changing the link shows a warning: the old link keeps redirecting (slug history) and table QR codes keep working. Editing infos no longer turns ordering back on; clearing the WhatsApp number turns it off.
99. **Hours: up to 3 slots a day**, Saturday first (restaurant week), "copy to all days", slots past midnight allowed. Closing days are dated exceptions with an optional reason shown on the menu. Hours, exceptions and links save in one RPC (one transaction). Instagram/Facebook/TikTok accept a handle or a URL; Maps and Google review links must be `https://`.
100. **One nightly endpoint** `POST /api/cron/nightly` (Bearer `CRON_SECRET`): subscription tick, then maintenance: issued codes past their timer → expired, unanswered requests after 1 day → cancelled, rate-limit rows older than 2 days deleted, AI import sources older than 30 days and photos of dishes deleted more than 30 days ago removed from Storage. The SQL part clears the rows and returns the paths; the route deletes the files (Storage files can't be removed from SQL). It replaces `/api/cron/subscriptions`.
101. **Error and loading states**: skeletons and a retry error boundary for the owner app and admin; menus get a bilingual inline error screen (no message bundle shipped to diners).
102. **Docker**: Next standalone output on `node:22-bookworm-slim`, non-root, health check on `/connexion`; `NEXT_PUBLIC_*` are build args. The admin bootstrap script is bundled with esbuild so it runs inside the slim image. The base image is a build arg (`NODE_IMAGE`) for registries that rate-limit.
