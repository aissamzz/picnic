# Decisions

Defaults picked while building, so they can be revisited in one place.
Format: what, why, and how to change it.

## Phase 1: Foundation

1. **No locale segment in URLs.** Locale = `?lang=fr|ar` (sets a cookie) → `NEXT_LOCALE` cookie → `Accept-Language` → French. The spec's routes (`/tarifs`, `/app/menu`) carry no locale, and a root `[locale]` segment can't coexist with the root `[slug]` public menus. Static routes win over `[slug]`, and every top-level route name is in `reserved_slugs`. Public menus fall back to the restaurant's `default_locale` (phase 3).
2. **Tailwind v4 + shadcn/ui conventions.** `components.json` is configured (new-york, lucide, `@/components/ui`, `cn` in `lib/utils/cn.ts`) so `pnpm dlx shadcn add <x>` works. The base components are hand-written on Radix primitives to use our tokens and logical properties rather than shadcn's default theme.
3. **Library versions:** Next 15.5, React 19.1, next-intl 4, Zod 4, `@tanstack/react-table` pinned to v8 (v9 changed its API), vaul for bottom sheets, sonner for toasts, react-easy-crop for the cropper.
4. **Billing columns hidden with column grants.** `authenticated` cannot select `plan`, `paid_until`, `payment_reference`, `referral_code`, `referred_by` on `restaurants`. Owners and super admins read them from the `restaurant_billing` view. `status` and `trial_ends_at` stay readable by staff because the app needs them to show the locked state.
5. **Restaurant creation, slug changes, status changes go through RPCs** (no direct insert on `restaurants`). `change_slug()` keeps the old slug in `slug_history` forever.
6. **Subscription lock is enforced in RLS**, not only in the UI: `can_edit_menu()` / `can_edit_settings()` return false when status is `expired` or `suspended`. Handling waiter calls stays allowed when expired.
7. **Staff vs owner split:** staff write menu tables (categories, items, variants, extras, schedules). Tables, hours, exceptions, social links, delivery zones and restaurant settings are owner-only writes; staff can read them.
8. **`restaurant_id` is denormalized onto `item_variants` / `item_extras`** (kept in sync by trigger) so RLS checks are a single function call.
9. **`menu_events` is indexed, not partitioned:** btree on `(restaurant_id, created_at desc)` + BRIN on `created_at`. Partition by month if it passes ~50M rows.
10. **Payment references** come from a sequence: `QR-0001`, `QR-0002`, … Referral codes are 6 chars without ambiguous letters.
11. **Weekdays are 0 = Sunday … 6 = Saturday** (JS `Date.getDay()`), times in the restaurant's timezone.
12. **Wilaya codes 1–58** (2019 division; list in `lib/dz/wilayas.ts`). Phase 2 tightened the original 1–69 check.
13. **Arabic prices render `1200 دج` as an isolated LTR run** (`<bdi dir="ltr">`), digits always Western; French uses U+202F as thousands separator.
14. **Local DB tests without Docker:** `pnpm db:test` boots a throwaway Postgres, loads `supabase/tests/local/supabase_shim.sql` (roles, `auth.uid()`, storage schema, a tiny pgTAP subset), then migrations, seed and `supabase/tests/*.sql`. The same `rls.sql` runs unchanged under `supabase test db`.
15. **DB types** are generated by `pnpm db:types` (our introspection script, same shape as `supabase gen types`). Swap to `supabase gen types typescript --local > lib/supabase/types.ts` whenever the Supabase CLI and Docker are available.
16. **`/dev/ui` is hidden in production** unless `ENABLE_DEV_UI=true`.
17. **Plan prices** in `platform_settings`: 2 500 DA/month, 13 500 DA/6 months, 24 000 DA/year, kit 6 000 DA (confirmed). Editable in admin settings (phase 8).

## Phase 2: Auth + onboarding

18. **Name and domain: Liinky, `liinky.app`** (`APP_NAME`, `NEXT_PUBLIC_APP_DOMAIN`).
19. **No SMS anywhere.** Accounts are phone + password, password typed twice at signup, no code at signup.
20. **Phone identity without SMS:** Supabase Auth's phone login requires an SMS provider, so each phone maps to a fixed internal email `p213XXXXXXXXX@phone.invalid` (`.invalid` is reserved and can never receive mail). `profiles.phone` (unique) is the real identity. Accounts are created server-side with the service key, so **public signup must be disabled** in Supabase Auth settings (`GOTRUE_DISABLE_SIGNUP=true`). Email confirmation is irrelevant (created as confirmed).
21. **Admin-issued codes** (`phone_codes`) replace OTP for (a) "Vérifier mon numéro" in account settings and (b) "Mot de passe oublié". The user asks; the request shows up on `/admin/codes`; the admin calls, generates a 6-digit code and reads it out. Codes live **2 minutes** (`code_ttl_seconds`), allow **5 attempts**, are stored as SHA-256 hashes (salted with the request id) and shown to the admin once. Admins can also generate a code with no prior request (during a call). Both waiting screens poll every 3 s and show the countdown. A successful password reset also marks the phone verified (the admin called that number).
22. **"Mot de passe oublié" says when a number has no account.** It helps owners who mistype; the risk (learning that a phone belongs to a restaurant owner) is low and the endpoint is rate-limited.
23. **Phone verification is optional** and doesn't gate anything yet; the home screen nudges until it is done.
24. **One owned restaurant per account** (`create_restaurant` refuses a second). Staff can belong to others via invites.
25. **Uploads go through server actions** (validated + resized with sharp, stored with the service key), never directly from the browser. Storage RLS policies stay as defense in depth.
26. **Onboarding step 4 (AI review) is skipped** until phase 6: step 3 goes straight to 5. Photo/PDF import buttons show "Bientôt".
27. **Restaurant default language = the language the owner used during setup.** Generated table labels ("Table 3" / "طاولة 3") follow it.
28. **Slugs:** generated from the name and kept in sync until edited; Arabic-only names fall back to `restaurant-<commune>`. Availability is checked live with a free alternative suggested.
29. **No first-order check for diners** (confirmed). `first_order_otp` stays false; abuse is handled by fake-order flagging and platform-wide blocked phones (phase 5).
30. **Temporary public menu page** at `/[slug]` proves links work (slug history 301s, table vs order mode, paused state). Phase 3 replaces the rendering with the 9 templates.
31. **Docker-free dev stack** (`pnpm stack:start`): Postgres + GoTrue + PostgREST binaries + a small Node gateway that also serves Storage from disk (no storage RLS there). Prefer `supabase start` when Docker exists.

## Phase 3: Public menus

32. **Two root layouts.** `app/(site)` (marketing, auth, owner app, admin) and `app/(menu)` (public menus). Menus get a cookie-free `<html>` with no i18n runtime, toaster or app fonts, so they can be statically cached and stay light.
33. **Menu URLs are rewritten, not routed.** The middleware turns `/{slug}` and `/{slug}-menu` into `/r/{lang}/{segment}`, an ISR route (`revalidate = 3600` + on-demand `revalidateTag("menu:{slug}")` from every owner edit). Language order: `?lang=` > diner's cookie > browser `Accept-Language` > restaurant default (`default` variant). Every first path segment owned by the app is listed in `lib/routes.ts` and must be a reserved slug (unit-tested). Note: Next marks rewritten responses `Cache-Control: private`; the server-side ISR cache still serves them (~20 ms). Only matters behind a CDN.
34. **Old slugs 301 in the middleware**, which can keep `?t=` (printed table QR codes) and `?src=`. It asks `resolve_public_slug` and caches the answer per instance for 60 s. The page keeps a query-less fallback redirect.
35. **Device-side state.** The cached HTML is shared, so time- and visitor-dependent things are computed in the browser: open/closed (restaurant time zone), menu schedules, the table label from `?t=`, favorites (localStorage per restaurant), analytics beacon.
36. **Templates = one shared `MenuApp`** (search, scrollspy tabs, item and info sheets, favorites, analytics) + per-template `Header`, `CategoryTabs`, `ItemCard`, `ItemSheet` (+ optional `SectionHeader`, `DishOfDay`) and a `--m-*` theme. The template is picked in a client component with `next/dynamic`: a server-side import of all nine put every template into the page's chunks.
37. **Sheets use native `<dialog>`** (focus trap, Esc, inert background) instead of a dialog library, to keep diners' JS small.
38. **Fonts on menus are self-hosted** (`public/fonts/menu`, fetched by `scripts/fetch-menu-fonts.mjs`, all OFL). Each page preloads only its template's display face (+ Cairo Arabic on Arabic pages); Latin body text uses the system UI font. `next/font` remains for the site/app, with `preload: false` because Next attached those preloads to menu routes through the shared stylesheet. Result: LCP 1.7–2.3 s, Lighthouse mobile performance 97–99.
39. **JS budget.** Table mode loads ~148 KB gzipped: ~125 KB is the React 19 + Next 15 App Router runtime (present on every App Router page), ~15 KB shared menu code (incl. `next/image`), ~8 KB for the chosen template. The spec's < 100 KB isn't reachable with the App Router runtime alone; the Lighthouse target (≥ 90) is met with margin. Going lower would mean serving table mode outside React (static HTML + a small script).
40. **Public menu code avoids `tailwind-merge`** (`cx()` instead of `cn()`), saving ~8 KB.
41. **Table links are `noindex`** (duplicates of the order link) and canonical to `/{slug}`. Lighthouse SEO on table links is 90 because of that, by design.
42. **Preview route** `/apercu/{template}/{fr|ar}/{slug}`: any restaurant in any template and language, uncached, no analytics, `noindex`. Used for template QA now and the appearance editor's live preview in phase 4.
43. **Order mode in phase 3 = browse only** (sizes and extras shown in the item sheet). Cart, checkout and WhatsApp land in phase 5; the waiter-call button with them.
44. **Photos:** seed items have none, so cards show a themed initial placeholder. Photo-heavy layouts (Grill rows, Traditionnel dish of the day) shrink when there's no photo.

## Phase 4: Owner menu management

45. **Multi-row writes go through `SECURITY INVOKER` RPCs** (`save_item`, `reorder_*`, `set_prices`, `bump_prices`, `save_translations`): one transaction, while RLS and the subscription lock still decide. `save_item` replaces sizes and extras wholesale.
46. **Staff manage the menu** (categories, items, prices, translations, schedules, sold-out) and can see the share hub. Appearance and tables are owner-only, like other settings.
47. **Deletes are soft with an Undo toast** (categories, items). Tables are hard-deleted after a confirm sheet (calls and events keep `table_id = null`).
48. **Sold-out toggles are optimistic** with Undo; a failure (e.g. expired subscription) rolls the switch back and shows why.
49. **Bulk price change is an amount in DA** (+50 / -20) on the whole menu or one category; sizes follow; never below 0. No percentage: Algerian menus move in round DA steps.
50. **Brand color is a fixed palette** of 8 colors that all keep white text at 4.5:1 (plus "template color"). Picking one also sets the template's on-accent text to white.
51. **Live preview** is an iframe of `/apercu/...` with `?accent=` for the unsaved color; it reloads on template/color/language/logo/cover changes.
52. **Dish photos**: up to 4, cropped 4:3 in the browser, resized to WebP (max 1600 px) on the server, first one is the main photo. Removed photos are deleted from Storage on save; uploads abandoned before saving are left for a purge job (TODO).
53. **QR images are drawn in the browser** (canvas + `qrcode`, page fonts, so Arabic shapes correctly): QR PNG/SVG, Instagram story 1080×1920, post 1080×1080, per-table cards, ZIP via `jszip` (loaded on demand).
54. **The table PDF uses `@react-pdf/renderer` on the server** with static Cairo TTFs in `lib/pdf/fonts` (fontkit can't embed variable WOFF2). 6 cards per A4 page with the Kabyle band, QR, table name and the scan line in each enabled language.
55. **Tracked links**: the share hub lists `?src=ig|fb|tt|wa|poster` variants of the order link; visits per source over 7 days come from `channel_stats()`.
56. **Rate limits per IP are loose** (signup 30/h, login 100/15 min, reset 20/h) and skipped for loopback/unknown IPs: Algerian mobile carriers put many users behind one IP (CGNAT). Per-phone limits do the real work.
57. **Dev stack tracks applied migrations** (`pnpm stack:migrate`).
